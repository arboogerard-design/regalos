Activa RLS y limita el acceso

  1. En Supabase abre tu proyecto y el SQL Editor. Revisa todas las tablas de los esquemas expuestos a la API.
  2. Revisa sus permisos y políticas existentes. Quita las políticas demasiado amplias: añadir otra restrictiva no elimina las anteriores.
  3. Activa RLS y concede solo los permisos necesarios. Este ejemplo supone una tabla public.reservas con user_id asociado al usuario de Supabase Auth:
alter table public.reservas enable row level security;
revoke all on table public.reservas from anon, authenticated;
grant select, insert, update, delete
  on table public.reservas to authenticated;

create policy "reservas_propias"
on public.reservas for all
to authenticated
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id);
  1. Repite con las reglas apropiadas para cada tabla. Prueba lectura, creación, edición y borrado con un usuario A, otro B y sin sesión: B no debe acceder a las filas de A. Revisa también vistas y funciones.

Dónde guardar las claves

Las claves secretas de OpenAI y Supabase van en variables de entorno privadas del servidor o en su gestor de secretos. El navegador llama a tu backend; el backend valida la sesión y los permisos y llama a la API. Evita prefijos que exporten secretos al cliente, como NEXT_PUBLIC_ o VITE_. No subas .env con secretos al repositorio. Si una clave se filtró, revócala y reemplázala.

La clave publicable de Supabase puede estar en el navegador. No sustituye las políticas RLS. service_role y las claves secretas tienen privilegios elevados: nunca en el frontend. El servidor también debe comprobar quién puede hacer cada operación.

Prompt exacto para Claude

Revisa mi app como si fueras un atacante, solo en este repositorio y en el entorno de pruebas que te indique. Usa datos ficticios. No pruebes servicios ajenos ni accedas a producción.

Empieza leyendo la arquitectura y enumera los puntos donde un visitante podría leer datos o provocar gasto. Busca secretos incluidos en el frontend, bundles, repositorio, respuestas y logs. No imprimas sus valores: informa solo del archivo y ubicación.

En Supabase comprueba RLS y permisos de todas las tablas expuestas, las políticas existentes, vistas y funciones. Revisa el aislamiento entre usuarios y negocios y los usos de service_role. Comprueba la autorización en cada ruta del servidor y los límites de uso de APIs de pago.

Por cada hallazgo dame: evidencia concreta, impacto, archivos afectados, corrección mínima y prueba reproducible. Distingue lo confirmado de lo que no puedes verificar. Propón las correcciones y, en desarrollo, aplícalas y prueba que usuario A, usuario B y visitante sin sesión solo puedan realizar las operaciones permitidas. Repite las pruebas después de corregir. No cambies ni despliegues en producción.

Una revisión con IA ayuda a encontrar fallos; no certifica que la app sea segura. Conserva pruebas de acceso que permitan y rechacen operaciones, y vuelve a ejecutarlas tras cada cambio.
